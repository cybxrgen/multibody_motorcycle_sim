# Architecture

**Authoritative for:** the module inventory and responsibilities, dependencies, data flow and state ownership, architectural boundaries,
and design decisions with their rationale.
**Belongs elsewhere:** what is implemented/verified and known limitations → `PROJECT_STATE.md`; milestone status → `PHASE_PLAN.md`;
equations and sign conventions → `PHYSICS_CONVENTIONS.md`; test methodology → `TESTING.md`.
**Update when:** a module is added/removed/re-scoped, a dependency or ownership rule changes, or a design decision is made or reversed.
Describes only modules that exist; planned systems are not listed here until they are built.

## Principle
One authoritative simulation (`SimWorld`) owns all physical state. Motorcycle parts are independent rigid bodies coupled through generic constraints and explicitly modeled forces. Rider segments will follow the same multibody approach. Godot nodes only visualize published state. The core is generic: no vehicle or rider special cases.

## Dependency rule
`Presentation/Debug → Core/Solver`, never the reverse. `Motorcycle → Core/Solver` only: Core and Solver never reference `Motorcycle`, and `Motorcycle` never references the scene tree, `Presentation` or `Debug`. `Debug` may read a `MotorcycleAssembly` and its collision-box objects (read-only; `geometry_wireframe.gd`), and nothing in `Core`, `Solver` or `Motorcycle` depends on it. Core and Solver are scene-tree free (`RefCounted`; `SimConfig` is a `Resource`).
Scripts reference each other through `preload` constants (no `class_name`), so headless runs need no import step.

## State ownership and data flow
`SimWorld.bodies` owns the list; each `SimRigidBody` owns its pose, velocities and accumulators. `SimWorld.constraints` owns the constraints; each
constraint owns its rows (and their warm-start impulses). `SimWorld.force_providers` owns the force providers; a provider owns only its own parameters and reads body state. Only `SimWorld.step()` and the integrator mutate bodies during a step; the solver changes
bodies only through their velocities. External code may apply forces/impulses between steps. Render code reads `previous_state` / `published_state` only.

### Execution pipeline (`SimWorld._step_unchecked`, after `preflight`)
capture previous state → add gravity force (m·g) → **force providers** (`apply_forces(dt, config)` of every enabled provider, from the start-of-step state) → integrate velocities (F/m, torque, implicit gyroscopic update) → **state check** (dynamic velocities; poses of all bodies, static included) → zero split velocities → constraint prepare → **physical PGS pass** → **state check** (velocities) → **split-impulse PGS pass** →
integrate positions (x += (v + v_s) dt, q = exp((ω + ω_s) dt/2) q) → zero split velocities → **state check** (velocities and poses) → publish state → clear accumulators.
Stabilization is the split pass: positional error is corrected through temporary split velocities that move the pose and are never stored as physical velocity (decisions D13–D15).
The physical pass never reads split state and the split pass never reads or writes physical velocities or impulses (it reads only poses and inertia through the shared Jacobians), so the ordering only fixes determinism. Friction, motor and speculative biases live entirely in the physical pass; `SimWorld` and `ConstraintSolver` contain no joint- or contact-specific stabilization logic.

### Integration method
Semi-implicit Euler (velocities first, positions from the new physical velocities plus the split velocities of the step). Rotation uses the exact exponential map of the new world-frame ω applied as a
pre-multiplied increment, then normalizes. The torque is a first-order kick; the gyroscopic part is an implicit midpoint step of Euler's equations in the body frame,
which conserves `|L|` and the rotational kinetic energy of a torque-free body exactly and therefore bounds `|ω|` for any dt (equations, properties and limits:
`PHYSICS_CONVENTIONS.md`, "Rotational dynamics"; decision D16). The world-frame direction of `L` is only first-order accurate.

## Validation and failure behavior
- Rules live in two places only: `SimConfig.validate()` (parameters) and `SimMassProperties.validate_inertia()` plus the constructor (mass/inertia);
  constraints validate their own data in `SimConstraint.validate()` (empty = valid). Rules: `PHYSICS_CONVENTIONS.md` (inertia), `sim_config.gd` (config ranges). Nothing is clamped or repaired.
- `SimWorld.preflight()` runs at the start of **every** `advance()` and `step()` (`SimConfig` and constraint data are mutable after construction). If the
  config (or a null config), any body's mass properties, any constraint's data, or any constraint's world membership is invalid: `advance()` returns 0, `step()` returns false, **no state is touched**
  (accumulator, bodies, force accumulators, step count, time), `rejected_step_count` increments, `last_error` holds the reason, and `push_error` fires once per
  distinct message (not per call). Fixing the cause resumes simulation.
- `SimWorld.add_body()` returns null for invalid mass properties; `SimWorld.add_constraint()` returns null for a null constraint, a constraint with a null body or a body that is not a registered member of this world, or invalid constraint data.
  `interpolation_alpha()` returns 0 for an invalid timestep. `step()` returns bool; `SimRigidBody.set_mass_properties()` returns bool.
- `SimWorld.add_force_provider()` returns null for a null provider, a provider that involves a null body or a body that is not a registered member (identity), or invalid provider data (`validate()`); `preflight()` re-checks membership and `validate()` of every provider every step, exactly like constraints.
- `BallJointConstraint` inherits the always-valid default. `HingeJointConstraint` and `ContactConstraint` validate their own data in `validate()` (nothing is duplicated in `SimWorld`), so invalid contact data is refused both by `add_constraint()` and by `preflight()` after later mutation.

### Numerical failure containment (D17)
`SimWorld` checks the state at three points of every step: after the velocity integration and before the constraint solve (a failed gyroscopic solve; non-finite linear/angular/split velocity of dynamic bodies;
non-finite position or a non-finite / non-unit orientation beyond 1e-5 of **every** body, static bodies included, plus a non-finite world inertia of dynamic bodies), after the constraint solve
(velocities), and after the position integration (velocities and poses again) — in this order so that a bad value never enters the solver and never reaches `published_state`.
Static bodies are exempt from the velocity and world-inertia checks only: their pose is published and read by constraints like any other. Everything the check rejects is only detected, never repaired. On the first violation the step is **aborted**: every body is restored to the state captured at the start of the step (`previous_state`),
forces and split velocities are discarded, nothing is published, time and `step_count` do not advance, `numerical_fault` / `last_error` record the body id, name, quantity,
stage and step, and `push_error` fires once. The internal step reports success explicitly: `step()` returns true only for a completed step and false both when preflight refuses
it (counted in `rejected_step_count`) and when it was aborted (not a rejection). While `numerical_fault` is set `preflight()` refuses all steps (`step()` returns false, `advance()` returns 0)
until `clear_numerical_fault()`. There is no clamping or repair of velocities or poses; the check only detects.

Rollback restores the state captured at the start of the *aborted step*, not the last published state. If the caller corrupted a pose before `step()` (for example a static body's position set to NaN), that pose is already in the snapshot,
so it is detected before the constraint solve, the step aborts, and the rollback restores the same invalid pose. `clear_numerical_fault()` only clears the flag; it does not repair body state, so the next step detects the invalid pose
again. The caller must restore a valid position/orientation (or remove and recreate the body) and then call `clear_numerical_fault()`. This is deliberate rollback behaviour, not an automatic-recovery guarantee (`PROJECT_STATE.md`, limitations).

`advance()` policy after a fault: the first aborted step ends the call immediately; `advance()` returns only the steps that completed. The aborted step is not counted and its `dt` is not
subtracted, so the accumulator keeps the aborted step's time and all unattempted time (including that call's frame time); the backlog guard does not run, so no time is dropped. Later calls
are refused by `preflight()` (the refused frame time is not accumulated), so a failed step is never retried automatically; after `clear_numerical_fault()` the preserved time is consumed
normally (still subject to `max_steps_per_frame`).

Constraint solver state: the solver rewrites the carried warm-start impulses (row `accumulated_impulse`, `ContactConstraint`'s world-space friction impulse) before a fault can be detected
after the solve, possibly with non-finite values. An abort therefore **invalidates** them: `SimWorld` calls `SimConstraint.reset_warm_start()` on every constraint (rows via
`ConstraintRow.reset_impulses()`), so the first step after `clear_numerical_fault()` starts from a cold, consistent solver state. Snapshot-and-restore was rejected: it would add a copy per row
to every normal step to preserve warm-start values of a world that, after a fault, has to be inspected and repaired by the caller anyway. The hinge angle tracker needs no handling:
the solver only samples the unchanged start-of-step poses, which equal the restored poses.

## Motorcycle assembly (M2.1, front fork extended in M2.2, rear suspension in M2.3)
`Simulation/Motorcycle/` builds the vehicle **on top of** the generic simulator; it adds no motorcycle logic to `Simulation/Core` or `Simulation/Solver`.
Body / joint graph (joint between A and B; the hinges are unmodified `HingeJointConstraint`s, the fork joint a generic `PrismaticJointConstraint`, all registered in one `SimWorld` with their bodies; the two spring-dampers are force providers of the same world):

```
chassis --steering_head (axis: raked steering axis)--> steering (steering stem + upper fork structure)
   |                                                        \--fork_travel (prismatic, along the fork axis = steering axis)--> fork_slider (lower fork + axle carrier)
   |                                                                                                                         \--front_axle (+X)--> front_wheel
   \--swingarm_pivot (+X)--> swingarm --rear_axle (+X)--> rear_wheel
        front suspension: spring-damper force provider between steering and fork_slider, along the fork axis
        rear suspension:  spring-damper force provider between chassis and swingarm, along the line between two attachment points (no joint, no body)
```
All six bodies are dynamic with their own mass and full inertia tensor about their own COM; nothing is merged into the chassis or into each other (the slider is not merged into the wheel or the steering assembly). Each hinge frees exactly one relative rotation and
constrains the other five relative DOF (3 translation, 2 rotation); the prismatic joint frees one relative translation and constrains the other five. The hinges have no limits, motor, spring or damper; the fork has the spring-damper and travel limits; the swingarm hinge is free but the chassis and swingarm are coupled by the rear spring-damper force pair; a ground is optional (M2.4.1) and there is no tire force model or drive. The assembly is a free 6-body tree with 4 internal rotational DOF and 1 internal translational DOF.

Construction contract: the configuration gives geometry **once**, in world coordinates at the reference pose (COM poses, and for each hinge a pivot point and axis). The
builder derives each body's local anchor, axis and reference direction with `HingeJointConstraint.from_world`, using one deterministic world reference direction per hinge
(`hinge_reference`: the world basis vector least aligned with the axis, projected perpendicular to it; the fork joint uses the same helper). The two local axes and reference vectors of a hinge are therefore
generally different vectors (fork frame rotated by the rake, swingarm frame by its tilt), while the world frames coincide: zero anchor error, zero axis error, zero angle.
`construction_error()` re-checks this (anchors 1e-5 m, axes 1e-5 rad) on the finished assembly. Failure policy follows `add_body` / `add_constraint` / `from_world`:
`build()` returns null with `push_error`; an invalid configuration is rejected before anything is registered, and any later failure (mass properties, `add_body`, hinge
creation, prismatic joint creation, `add_constraint`, front and rear suspension creation, `add_force_provider`, construction contract) removes exactly the bodies, constraints and force providers this call added (a passed-in world keeps its earlier content; body ids are not reused).
The prototype fixture is deliberately separate from the schema (`motorcycle_prototype.gd`) and is labelled illustrative.

Sign conventions of the fixture (not of the schema; the axis sign in the config defines the positive angle): steering hinge positive = steering left; swingarm positive = rear end down;
wheel axle +X, so rolling forward is a negative rate about the axle axis.

## Front suspension (M2.2)
Update flow per fixed step: `SimWorld._step_unchecked` → gravity → `FrontSuspension.apply_forces(dt, config)` (reads the fork joint's world axis and the two bodies' current poses and velocities; `apply_force_at_point` on the slider and, reversed, on the steering assembly) → velocity integration → solver (the prismatic rows constrain the five directions and the limits act on the axial one) → position integration. Dependencies: `FrontSuspension → SimForceProvider` (Core), `PrismaticJointConstraint` (read-only queries), `SimRigidBody`; nothing in Core or Solver references the suspension. The spring seats and the axis come from configuration world geometry (builder: `FrontSuspension.from_world`); the prismatic joint's axis points from the steering assembly toward the slider, so a positive coordinate is fork extension. Equations, signs and energy behaviour: `PHYSICS_CONVENTIONS.md` ("Prismatic joint", "Front suspension spring-damper").

## Rear suspension (M2.3)
Update flow per fixed step: `SimWorld._step_unchecked` → gravity → each registered provider in registration order (front, then rear) → velocity integration → solver → position integration. `RearSuspension.apply_forces(dt, config)` reads the two bodies' current poses and velocities, forms `d = p_s - p_c`, `n`, `l`, `l_dot` from the attachment points and applies `+F n` at `p_s` to the swingarm and `-F n` at `p_c` to the chassis (`apply_force_at_point`). Dependencies: `RearSuspension → SimForceProvider` (Core) and `SimRigidBody`; it references neither a joint nor the prismatic/hinge solver code, and nothing in Core or Solver references it. The attachment points come from configuration world geometry (builder: `RearSuspension.from_world`). The provider is held by `MotorcycleAssembly.rear_suspension` and is the second entry of `world.force_providers`. Equations, signs and the degenerate-geometry threshold: `PHYSICS_CONVENTIONS.md` ("Rear suspension spring-damper").

## Ground contact (M2.4.1)
**Ownership.** The ground is a static `SimRigidBody` (`ground`, zero inverse mass, identity orientation at the plane point) registered in the same `SimWorld` as the motorcycle; the wheel contacts are `WheelGroundContact` constraints (`Simulation/Motorcycle/`, a subclass of the generic `ContactConstraint`; body A = ground, body B = wheel) registered in `world.constraints`. `MotorcycleAssembly` holds named references (`ground`, `front_wheel_contact`, `rear_wheel_contact`) and owns nothing physical. Ground and contacts exist only when `MotorcycleConfig.ground` is set (default null = the M2.1-M2.3 assembly). `Simulation/Core` and `Simulation/Solver` contain no ground, wheel or motorcycle logic and were not changed.
**Per-fixed-step update path.** `SimWorld._step_unchecked` → gravity and force providers → velocity integration → `ConstraintSolver.solve` → for every enabled constraint `prepare(dt, config)`. `WheelGroundContact.prepare()` runs there, from the start-of-step poses: it recomputes the wheel's lowest point, the plane point and the normal (`compute_geometry`), re-seats `local_anchor_a/b` and `local_normal_a`, decides activation, and then calls the generic `ContactConstraint.prepare()` (rows, speculative bias, split bias, warm start). Because the solver calls `prepare()` once per executed fixed step, a frame that runs several steps in `SimWorld.advance()` refreshes the geometry at every one of them (tested through `refresh_count` and an independent evaluation of the start-of-step pose) and a frame without a step refreshes nothing. No change of body state happens outside this lifecycle; a refresh uses the unchanged poses. This was possible without any generic extension (no callback framework); the alternative of re-seating the anchors from the scene once per frame was rejected because it is stale for every step but the first and runs at the render rate.
**Lifecycle.** A contact is active when the geometry is valid and `gap <= activation_distance + approach_speed * dt`. An inactive contact (separated, or degenerate geometry) calls `reset_warm_start()` (physical normal impulse and the carried friction vector), clears the row effective masses and the split flag, and its `solve_iteration()`, `solve_split_iteration()` and `finish()` do nothing: it adds no impulse and keeps no ghost state, and re-contact starts cold. Wheels approaching, touching, penetrating and separating are all handled by the generic rows (speculative `g/dt` bias, split-impulse penetration correction, unilateral normal, Coulomb disk); `contact_state()` is a diagnostic only. After an aborted step `SimWorld._abort_step` resets the warm start of every constraint, contacts included. Disabling the contacts (`set_ground_contacts_enabled(false)`) also discards the carried impulses; `remove_ground()` removes both contacts and the ground body, and `SimWorld.remove_body` drops a body's constraints in any case, so no orphaned constraint can remain.
**Validation and rollback.** The configuration (finite point, finite unit normal, finite friction >= 0, finite activation distance >= 0, wheel axles not parallel to the normal at the reference pose) is validated before anything is registered; the ground rules are repeated by `WheelGroundContact.validate()` and re-checked by `preflight()` every step, which also refuses a ground that has become dynamic. The builder registers the ground body and the two contacts after the suspension providers; a failure at any point removes exactly the objects the call added (ground body, contacts, joints, providers, bodies).
**Boundaries and dependencies.** `WheelGroundContact → ContactConstraint (Solver), SimRigidBody`; `MotorcycleBuilder → WheelGroundContact`; presentation reads published state and `WheelGroundContact.compute_geometry` (a pure function) for the markers. Nothing in Core or Solver references the motorcycle package. Geometry, approximation and operating domain: `PHYSICS_CONVENTIONS.md` ("Ground plane and wheel contact").
**Rejected / deferred.** A generic per-step "constraint refresh" hook in Core/Solver (not needed: `prepare()` is already the per-step hook; adding one would be the callback framework the assignment excludes); a general collision-detection layer (out of scope); tyre-width patches and multi-point manifolds (M2.5 or later); a roll-stabilizing stand or damping (never: it would hide the physics); collision of the other bodies with the ground (not needed for the foundation; see `PROJECT_STATE.md`).

## Tyre model (M2.4.2)
**Ownership.** A wheel with a tyre specification (`MotorcycleConfig.front_tire` / `rear_tire`, default null = the M2.4.1 generic contact) gets a `TireGroundContact` instead of a `WheelGroundContact` (`Simulation/Motorcycle/`; a subclass, so the geometry, activation and per-step re-seating of M2.4.1 are reused unchanged). `MotorcycleAssembly.front_tire` / `rear_tire` are named references to those contacts (the tyre IS the contact of its wheel: it references the right wheel and contact by construction) and own nothing. The tyre spec is copied by the builder; later edits of the configuration do not reach the simulation. `Simulation/Core` and `Simulation/Solver` were not changed; the only edit of M2.4.1 code is a one-method hook, `WheelGroundContact._prepare_active()`, whose default is the previous `ContactConstraint.prepare()` call.
**Friction ownership (decision).** M2.4.1 uses isotropic Coulomb friction inside `ContactConstraint`. Adding tyre forces on top would count the ground friction twice. The tyre contact therefore bypasses the generic friction block completely (`_prepare_active()` never warm starts it, `solve_iteration()` never solves it, `_solve_friction()` is empty) and re-aims the two tangent rows at the tyre axes; they carry only the tyre impulse. The unilateral normal row is the generic one and stays active. One owner per wheel: tyre if configured, generic Coulomb otherwise, never both. Tyre disabled = frictionless normal contact. Rejected: a force provider adding explicit tyre forces (explicitly unstable for the wheel's low axle inertia, uses a stale normal load, and cannot give an implicit slip response); clamping a generic Coulomb disk to the tyre limits (cannot represent slip-dependent, anisotropic forces); a generic tyre framework or a generic solver extension (not needed, excluded).
**Per-fixed-step order.** `SimWorld._step_unchecked` → gravity and force providers (external wheel torques of tests act here) → velocity integration → `ConstraintSolver.solve`: for every enabled constraint `prepare(dt, config)`; `TireGroundContact` then (1) refreshes the geometry from the start-of-step pose and decides activation, (2) re-derives the tyre axes, the slip rows, the 2x2 response `G`, the reference speed `D` and the frozen spin, (3) prepares and warm starts the normal row, (4) warm starts the carried tyre impulse (projected, scaled into the current ellipse). Then in each of the `solver_iterations` physical iterations: normal row → tyre tangential impulse from that iteration's normal impulse (the load) → rolling-resistance angular impulse. The split pass touches only the normal row (penetration), never the tyre. `finish()` stores the tyre impulse for the next warm start. Every internal fixed step of `advance()` repeats all of this from the then-current state; nothing is evaluated per rendered frame.
**Speculative contact is not tyre contact.** The generic normal row stays speculative (M2.4.1, unchanged); its positive impulse at a small positive gap is collision prevention. `TireGroundContact` computes `_touching = gap <= TOUCH_TOLERANCE` in `_update_rows()` (the start-of-step gap the normal row uses; the constant is the existing one of `WheelGroundContact`, no new tolerance) and gates every tyre effect on it: `_prepare_active()` clears the carried tyre impulse instead of warm starting it, `_solve_tire()` and `_solve_rolling_resistance()` have a zero target, `normal_load()` and `friction_utilization()` report zero physical load. Rejected: changing the generic speculative policy or the activation distance (it would hide a tyre-specific defect and alter the M2.4.1 contact); gating on the sign of the normal impulse (that is exactly the defect).
**Normal load.** `N = lambda_n / dt` from the accumulated physical normal impulse of the same iteration (units: impulse over the fixed step), only while the wheel is geometrically touching (see above). An inactive contact discards all impulses in `reset_warm_start()` (also overridden to clear the tyre impulse and the rolling-resistance impulse), so there is no load, no tyre force and no rolling moment after separation, and re-contact starts cold. Slip, load and forces of the last step are read by queries; slip can also be evaluated from any state with the pure `TireModel.slip`.
**Why the tangential response is implicit inside the solver.** The slip stiffness of a tyre is large compared with the wheel's axle inertia (`c R^2 dt / I > 2` for the prototype wheel), so an explicit per-step force diverges; the closed-form 2x2 implicit solve per iteration is stable for any stiffness and needs the same-iteration normal load, which only the solver has. The ground is static and takes no impulse; the wheel receives the linear and the angular (`r x P`) response from one impulse at the contact point.
**Boundaries and dependencies.** `TireGroundContact → WheelGroundContact, TireModel, MotorcycleTireSpec`; `TireModel → WheelGroundContact.compute_geometry` (pure); `MotorcycleBuilder → TireGroundContact`; presentation/HUD reads published state and `TireModel.slip`. The builder's rollback is unchanged and covers the tyre contacts (they are the wheel contacts). Equations, signs and units: `PHYSICS_CONVENTIONS.md` ("Tyre behaviour"). Limitations and verification: `PROJECT_STATE.md`, `TESTING.md`.
**Rejected / deferred.** Relaxation length and tyre deformation, a full empirical (Pacejka) model, camber thrust, tyre width/contact patch, load sensitivity, temperature/wear (all excluded by the assignment or later work); engine, clutch, gearbox, final drive, rider and automatic control (M2.5/M2.6 and later, not implemented).

## Finite-width tyre geometry (M2.5.1)
**Ownership.** `TireGeometry` (`Simulation/Motorcycle/tire_geometry.gd`, `RefCounted`) is plain data (`width`, `crown_radius`) plus `validate(wheel_radius)` (the single home of the rules; `MotorcycleConfig` only calls it, prefixed `front`/`rear`) plus pure static functions. `MotorcycleConfig.front_tire_geometry` / `rear_tire_geometry` (default null = no geometry, every earlier configuration is unchanged) are independent objects (the same instance for both is rejected) and independent of `front_wheel_width` / `rear_wheel_width`, which stay visual/inertia dimensions. The builder validates them with the rest of the configuration before registering anything and stores copies in `MotorcycleAssembly.front_tire_geometry` / `rear_tire_geometry`; later configuration edits do not reach the assembly.
**API.** `TireGeometry.lowest_point(position, orientation, geometry, wheel_radius, plane_point, plane_unit_normal)` returns the lowest point of the finite-width surface; `point_at_offset(..., lateral_offset)` returns the lowest point of the single circle at a given offset across the tread (the building block a sampled patch can use). Both return one dictionary (`valid`, `reason`, `axle`, `normal`, `wheel_point`, `ground_point`, `gap`, `lateral_offset`, `lateral_fraction`, `at_shoulder`, `unclamped_offset`, `profile_radius`, `radial_direction`, `local_point`) with finite placeholders when invalid; `profile_radius(wheel_radius, offset)` and `shoulder_drop()` expose the profile. Nothing that can vanish is normalised, and invalid dimensions, non-finite or non-unit input and overflowing results are reported, never passed on. Equations: `PHYSICS_CONVENTIONS.md` ("Finite-width tyre geometry").

**Visualization (M2.5.1.2, reworked in M2.5.2).** `Debug/geometry_wireframe.gd` draws the physical collision boxes (see the next section) and, separately, the tyre surfaces of wheels with a `TireGeometry` (geometry only); the `visual_size` / wheel-dimension boxes were removed so that there is one authoritative source of box geometry. Presentation only: it adds no state, force or constraint to `SimWorld`.
**Dependencies and boundaries.** `TireGeometry` depends on nothing (not on the scene tree, bodies, the solver or `WheelGroundContact`); `MotorcycleConfig`, `MotorcycleBuilder` and `MotorcycleAssembly` depend on it. The wheel-ground contacts and the tyre model do NOT use it yet: contact, normal response and tyre forces are the one-point M2.4.1/M2.4.2 behaviour. M2.5.2 (not started) can sample `point_at_offset` across the tread without replacing the profile model.
**Rejected / deferred.** Putting the geometry into Core/Solver or a generic tyre framework (motorcycle-specific, excluded); making the wheel contact use the finite-width point now (that changes contact behaviour and is M2.5.2 or later); a measured or tabulated profile (not warranted for this simulator at this stage); deriving the width from `front_wheel_width` (those are visual/inertia dimensions and must not be conflated).

## Collision boxes, box-ground contacts and basic controls (M2.5.2)
**Ownership.** `MotorcycleConfig` holds up to four `MotorcycleCollisionBox` specs (`chassis_box`, `steering_box`, `fork_slider_box`, `swingarm_box`; null = no collision geometry) and an optional `MotorcycleControlSpec`. The builder stores an independent copy of each box in `assembly.collision_boxes` (by owner name) — the SAME object that the contacts and the wireframe read — and, when the configuration has a ground, registers eight `BoxGroundContact` slots per box (ground = body A, the owner = body B) in `assembly.box_contacts`. No body, joint or provider is added for the geometry; wheels never own a box and never get a box contact: the `TireGroundContact` stays their only ground contact (registered exactly once per wheel). Construction stays transactional (failure while registering any box contact or the controls removes every body, constraint and provider of the call).
**Contact generation.** A slot is one corner of one box (corner order = bit 0 x, bit 1 y, bit 2 z of the half-extent signs). Each fixed step `prepare()` re-derives the corner from the start-of-step pose, re-seats the anchors and normal, and is active iff the corner is finite and its gap is at most `activation_distance + approach speed * dt` (speculative, like the wheel contact). Selection is therefore a pure function of pose and velocity with fixed slot identity: no tie-breaking, the same corners every step for unchanged geometry; coplanar corners are all kept (a face needs them against tipping). An inactive slot discards its normal and friction impulses, so re-contact starts cold. The generic solver is unchanged; normal response, split-impulse penetration correction and Coulomb friction (the box's `friction`) are the generic contact's. An invalid box makes `validate()` report errors and `SimWorld` refuses to step; removing a body removes its slots (`remove_body`), removing a box does (`MotorcycleAssembly.remove_collision_box`).
**Controls.** `MotorcycleControls` is a `SimForceProvider`: it is evaluated once per fixed step (never per render frame) and uses only the torque API and the existing steering-hinge motor. Inputs are validated, not clamped (`set_inputs`). Throttle: axle torque on the rear wheel (reaction on the swingarm); brake: torque opposing the relative spin of each wheel against its carrier, capped at half the one-step stopping torque of the reduced inertia; steering: hinge motor target rate and torque cap, optional symmetric hinge limit configured by `MotorcycleControlSpec.steering_limit`. Input handling lives in the scene; physics code never reads the keyboard. Details and signs: `PHYSICS_CONVENTIONS.md`.
**Rejected / not done:** box contacts for the wheels (would double the normal support of the tyre contact), contact manifolds or face/edge reduction (all corners kept instead), box-to-box collision, a single rigid motorcycle body, a powertrain.

## Tyre surface sampling (M2.5.3 Stage A)
`Simulation/Motorcycle/tire_patch_sampler.gd` is a pure static `RefCounted` function (`TirePatchSampler.sample`): it takes a wheel pose, a `TireGeometry` and a plane, and returns the candidate surface samples on a bounded grid. It uses `TireGeometry` for the profile radius and the crown radius and owns only the parameterisation and the quadrature. It has no state, no solver dependency and no scene dependency, and is not yet registered anywhere in the assembly. Equations: `PHYSICS_CONVENTIONS.md` ("Tyre surface sampling").

## Tyre patch normal support (M2.5.3 Stage B)
`Simulation/Motorcycle/tire_patch_normal_support.gd` (`TirePatchNormalSupport`, a `SimConstraint`; body A the static ground, body B the wheel) is the per-wheel aggregate patch constraint, normal support only. Each fixed step `_update_rows` calls `TirePatchSampler.sample` (the profile is never re-derived), keeps the samples with a negative gap and owns one scalar soft row per such sample, keyed by the sample index (persistent rows give the warm start; rows of samples that left the ground are dropped). The rows are `VelocityJacobianRow` (a `ConstraintRow` subclass) and use the existing `softness`, `bias`, bounds and split impulse: the generic solver, `ContactConstraint`, `ConstraintRow` and `SimWorld` are unchanged. Each row carries two wheel-side angular Jacobians: the impulse side is the full wrench of a normal impulse at its sample (`J_ang = r x n`), the velocity side (compression rate, effective mass, split correction) is that vector minus its axle component, so axle spin never enters the normal solve while the physical moment is applied in full. Decision: a subclass was chosen over new `ConstraintRow` fields so that every existing constraint keeps its code path untouched; no solver change was needed. A compressed sample with a non-finite derived coefficient invalidates the whole patch for that step (rows, impulses and load cleared, `last_reason` set). The velocity-side effective mass is exact only when the wheel axle is a principal axis of the wheel inertia, so `validate()` enforces that precondition (static helper `axle_principal_axis_error`, in the body frame, scale-independent residual `|I u - u (u.I u)| / |I u| <= 1e-4` with `u` the body-local +X axle): a wheel whose tensor couples the axle (body-local +X) to the transverse axes is invalid, registration is refused and `SimWorld.preflight()` refuses to step; the inertia is never modified and the support never skipped. Queries: `normal_load`, `sample_report`, `total_force_world`, `total_moment_world`, `applied_wheel_moment`, `centre_of_pressure`, `contact_area`, `max_penetration`, `carried_impulse_total`. It is **not registered** by the motorcycle builder and does not feed the tyre-force model; the wheels still carry the one-point contact. Equations, units and limits: `PHYSICS_CONVENTIONS.md` ("Tyre patch normal support").

## Solver design
- Rows are scalar and solved sequentially (Gauss-Seidel); a ball joint is three rows along world axes, so its 3×3 block is not solved simultaneously.
  `solver_iterations` is configurable. Each iteration calls `SimConstraint.solve_iteration()` on every active constraint: the default solves its rows in order; a constraint whose rows are coupled overrides it.
- Warm starting: each constraint keeps its rows between steps and re-applies the previous accumulated impulse (scaled by `warm_start_factor`, clamped to the row limits).
  Ball-joint rows use fixed world axes so impulses stay meaningful.
- Split channel: each `ConstraintRow` carries `split_enabled`, `split_bias`, `split_min_impulse`, `split_max_impulse` and `split_accumulated_impulse` next to its physical fields. It reuses the row's Jacobian and effective mass and is solved against `SimRigidBody.split_linear_velocity` / `split_angular_velocity`. A row with `split_enabled = false` (the default, so hand-built rows are unaffected) is skipped. The split accumulated impulse is reset in every `prepare` (no warm start). Constraints fill the split fields in `_update_rows`: joint anchor and axis rows are always enabled (`split_bias = (β/dt) C`, bilateral); a hinge limit row and the contact normal row are enabled only while violated/penetrating (bounds `[0, +inf)`). Biases and equations: `PHYSICS_CONVENTIONS.md` ("Stabilization: split impulses").
- Row impulses obey `λ` along `Jᵀ`; ball-joint rows have `Jv_a = −Jv_b`, so linear momentum is conserved exactly and angular momentum up to `λ·(C × e)`, i.e. the (small) constraint error.
- Inactive hinge features (limits/motor off) keep impulse bounds [0,0]: `ConstraintRow.warm_start` clamps any carried impulse to 0 and `solve` applies nothing — no solver or row change was needed.
- Row layout, Jacobians, biases, angle tracking, limit and motor rules: header of `hinge_joint_constraint.gd` and `PHYSICS_CONVENTIONS.md` ("Hinge joint").
- Contact: 3 rows (normal, two tangent). The normal row is an ordinary scalar `ConstraintRow` with bounds `[0, +INF)`. The tangent rows only hold Jacobians and accumulated impulses; their solve is coupled (a disk whose radius is `mu` times the normal row's current impulse), so `ContactConstraint` overrides `solve_iteration()` (normal row first, then the friction block; the friction disk reads the physical normal impulse only) and `prepare()` (friction warm start projected into the current disk). Equations: `PHYSICS_CONVENTIONS.md` ("Contact"). The caller owns contact geometry (creation, anchor refresh as the patch moves, removal); the solver and `SimWorld` contain no contact logic.

## Decisions and rationale
- D1: custom engine only; no Godot physics objects as authority (task requirement).
- D2: COM is the body reference point; mesh offsets are presentation-only.
- D3: inertia stored as a full `Basis` to permit non-diagonal tensors.
- D4: no `class_name`, to avoid dependence on the editor's global class cache in headless mode.
- D5: no `force_accumulator.gd`, `impulse_solver.gd`, `rigid_body_dynamics.gd` (suggested layout): force/impulse logic is ~30 lines and lives on `SimRigidBody`; the "impulse solver" is the constraint solver.
- D6: invalid input is refused, never repaired or clamped (visible failure over hidden correction).
- D7: the only generic extension needed for the hinge was `SimConstraint.validate()`; the hinge extends `SimConstraint` directly and does not extend `BallJointConstraint` (kept isolated; the 3 anchor rows are duplicated on purpose).
- D8: hinge frame is defined by an explicit per-body reference direction (never singular, any orientation); `from_world()` (static factory in `hinge_joint_constraint.gd`) makes the creation pose angle 0.
- D9: hinge both limits enabled by one flag, finite bounds only; the motor target is clamped into the rate interval the limit rows admit so motor and limits never oppose.
- D10: world-membership invariant — every registered constraint's `body_a` and `body_b` are members of the same `SimWorld.bodies` (object identity, never body ids). Enforced generically for every `SimConstraint` subclass at `add_constraint()` and again in `preflight()` (the collections are public, so it is re-checked every step). `remove_body()` also removes every constraint that references the body (chosen over refusing the removal: `remove_body()`/`remove_constraint()` return nothing, and a constraint cannot outlive its body); unrelated bodies and constraints keep their order.

- D11: generic solver extension for coupled rows is one hook, `SimConstraint.solve_iteration()` (default loops the rows exactly as before; `ConstraintSolver` calls it instead of looping rows itself). `ConstraintRow`, `SimWorld` and the joints are unchanged. Chosen over a contact-specific branch in the solver and over a new row type: the friction disk couples two rows with a third, which a per-row `[min, max]` clamp cannot express.
- D12: contact friction is a circular Coulomb limit solved as a 2×2 block with K-metric projection (basis independent, maximum dissipation at convergence), not two clamped scalar rows. Friction is solved after the normal row in every iteration so the limit uses the current normal impulse. The shared world contact point (midpoint of the two anchors) is used for all lever arms so the impulse pair is collinear.

- D13: split impulses use the rows' existing Jacobians and effective masses through extra fields on `ConstraintRow` and one extra hook, `SimConstraint.solve_split_iteration()` (default loops the rows). Chosen over a second row class or a parallel constraint list (duplicated Jacobian construction) and over contact- or joint-specific branches in `ConstraintSolver`/`SimWorld`. `ConstraintSolver` only runs two passes; `SimWorld` only zeroes the split velocities around the solve and integrates them.
- D14: split velocities are scratch fields on `SimRigidBody` (so rows reach them like physical velocity), but are never part of physical state: temporary scratch quantities, zeroed before the solver and after the position integration, never published. *Direct isolation:* they are not included in the physical velocity, in the momentum or energy diagnostics, or in the motor, friction and contact-velocity calculations, which read the physical `v, w` only. They are not warm started (the accumulated split impulse is reset in `prepare`), as required for a correction that must not persist. *Indirect pose effects:* they are integrated into the pose, so a split angular correction can change a body's orientation. For an anisotropic body the new orientation changes the world-space inertia, so diagnostics calculated from the corrected pose and world inertia, such as spin angular momentum and rotational kinetic energy, can change indirectly although the physical angular velocity is unchanged. This is not a use of split velocity by the diagnostics; the physics is in `PHYSICS_CONVENTIONS.md` ("Stabilization: split impulses", orientation-dependent quantities).
- D15: the only stabilization parameter stays `SimConfig.baumgarte_factor` (beta); no new parameter, no hidden damping. Positional error uses `split_bias = (beta/dt) C`, the physical bias of the same row is 0 (joints) or the speculative `C/dt` (non-violated contact gap and hinge limit). The split pass is solved after the whole physical pass because the two do not interact.

- D16: the gyroscopic update is the implicit midpoint rule in the body frame (not the explicit term). Chosen because the explicit term has a one-signed second-order error that raises `T` and `|L|` every step and diverged for the inspection-scene spinner; the midpoint rule conserves exactly the two invariants that bound `|ω|`, adds no damping, needs no tuning parameter, and changes only `integrate_velocities` (torque path, orientation update, solver and split impulses untouched; bodies that do not change `L_b` are bit-identical to before).
- D17: numerical faults abort the step and roll back to the start-of-step state instead of clamping or repairing. Visible failure over hidden correction (D6); rollback keeps the world finite for diagnosis and keeps the renderer from ever receiving a non-finite transform.
- D18: the motorcycle is built from world-space geometry through `HingeJointConstraint.from_world`, not from per-body local offsets typed into the builder. Chosen so that anchors, axes and reference directions cannot disagree and the "bodies do not share local orientations" case (rotated fork and swingarm frames) is handled by the existing hinge convention instead of new code. Rejected: per-body local frames in the configuration (duplicated, unexplained offsets); a motorcycle-specific joint or a new constraint type (out of scope, and the generic hinge suffices).
- D19: the builder is all-or-nothing: validate first, register, then roll back exactly what it added on any failure; the construction check is a public function so it can be tested (honest input cannot trip it: pivots far from the origin stay self-consistent on the float32 grid, measured at 1e6 m).
- D20: M2.1 hinges are free (no limits, no motor): limits and actuators belong to later, explicitly authorized milestones; a hidden limit or stabilizer would be a hidden corrective force (`AGENTS.md` §4).

- D21: a generic per-step force-provider hook (`SimForceProvider`, `SimWorld.force_providers`) was necessary. Forces applied to a body are consumed and cleared by ONE fixed step, but `advance()` may run several fixed steps per frame; a state-dependent spring-damper applied by the caller once per frame would act on the first step only and be evaluated at the render rate, not the simulation rate. The hook is generic (the world knows nothing about suspensions), mirrors the constraint registry rules (membership by identity, validation at registration and in `preflight()`, removal with the body) and keeps all motorcycle logic in `Simulation/Motorcycle/`. Rejected: a suspension-specific branch in `SimWorld`; implementing the spring as a constraint (it is a force, with no impulse bounds or Jacobian rows); callbacks driven by the scene.
- D22: the prismatic joint is a generic constraint with 7 rows (the two limit rows exist always; inactive rows have bounds [0, 0], the hinge pattern). Its translation coordinate is the anchor offset projected on A's axis and the lateral rows move with A's frame, so their A-side angular Jacobian carries the `(r_a + d) × e` lever term (the axial offset swings the axis line sideways); this term was verified against central finite differences. The twist row uses the sine of the relative rotation about the axis, like the hinge's axis rows (valid only well below 90° of relative rotation).
- D23: the suspension force acts on the two spring seats, which must lie on one line parallel to the fork axis (a central, equal and opposite pair): a non-central pair would add angular momentum to an isolated system, and the seats are therefore validated, not repaired. The damping evaluates the seats' relative velocity from the start-of-step state (explicit), so the force pair injects no energy for any state; the stability of the explicit evaluation is a time-step condition on `k` and `c` (`PHYSICS_CONVENTIONS.md`), not a hidden correction.
- D24: the rear shock is a direct force pair between the chassis and the swingarm, modeled as a second `SimForceProvider`; it adds no body, no joint and no constraint row. The attachment points are arbitrary body-fixed points and the direction is recomputed from them at every step (not tied to a body axis, unlike the front suspension, whose axis is the prismatic joint's). Rejected: reusing `FrontSuspension` (it needs a joint and collinear seats); a massless shock body or a prismatic/distance joint for the shock (extra DOF and constraint rows for a force-only element); a rocker or progressive linkage (outside this increment); any direct pose or velocity edit.
- D25: degenerate attachment geometry (`l < MIN_LENGTH = 1 mm`, or a non-finite `l`: finite coordinates can still overflow the float32 length) is refused through the existing provider contract: `validate()` includes the current separation, so `add_force_provider()` and `preflight()` refuse it and the world does not step (visible failure over hidden correction, D6). Rejected: clamping the length, substituting a fallback direction, or silently applying zero force during stepping. The zero force in `apply_forces()` for such a state exists only so a direct call can never produce a non-finite force; the world never reaches it.

### Rejected / deferred options (with reasons)
- Explicit gyroscopic term (previous implementation): unconditionally energy- and momentum-increasing, unstable over long runs (`PHYSICS_CONVENTIONS.md`). Single-step linearized implicit Euler gyroscopic solve: stable but dissipative, would damp intermediate-axis tumbling. Moving the free-rotor step into the position phase (exact `L` direction): larger change to the step structure; deferred.
- Velocity clamping or `|ω|` caps, silencing the Godot error: rejected (hide the failure, no physical basis).
- 3×3 block solve: rejected for now (specification asks for scalar rows); remains an option for the known convergence limits (`PROJECT_STATE.md`).
- Split impulses via a separate position-level (nonlinear Gauss-Seidel) pass, a pose teleport, or a warm-started split impulse: rejected for M1.3. The first changes the row/Jacobian model and risks hidden corrections; a teleport is forbidden (`AGENTS.md` §4); a warm-started split impulse would carry a correction velocity across steps. Interleaving the split row with the physical row (solving both in one iteration) was not needed because the passes do not interact.
- Contact friction as two independently clamped scalar rows (square/pyramid region): rejected, anisotropic (allows `√2·mu·lambda_n` on diagonals) and dependent on the basis; and as radial Euclidean scaling of the block update: rejected, loses maximum dissipation for anisotropic `K`. Contact normal frame in world space only: rejected, a normal stored in body A's frame follows A's orientation (anchors still need caller refresh).
- Hinge: wrapped `atan2` as angle state (jumps at ±π; the continuous accumulated angle is used); an arbitrary perpendicular basis for the axis rows (singular cases); re-ordering rows (anchor rows last: measured identical result); extending `BallJointConstraint`; damping or more iterations as a fix for limit behaviour.
